# Tasks: Grounnel — Frontend Fact-Check UI

**Input**: [plan.md](plan.md), [spec.md](spec.md)

**Path convention**: `frontend/src/...` only — no backend tasks. The proxy is already complete and live-verified (`plan.md` § "Backend (already complete)"); this feature is a pure consumer of `POST /api/grounnel/extract` + `GET /api/grounnel/status/:id`.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel with other same-phase `[P]` tasks — different files, no dependency on another task in the *same* phase. A task can still be `[P]` while depending on an earlier, already-checkpointed phase's task (e.g. T006 depends on T005 from Phase 1, but is `[P]` relative to its Phase 2 siblings T007/T008).
- **[Story]**: Which user story this task belongs to (US1/US2/US3, spec.md priorities). Foundational tasks carry no Story tag, matching `001-reflection-flow/tasks.md`'s own convention.

## Phase 9: Fallback-tier visual distinction, date-fragmentation fix

**Goal**: real-run testing (Bukowski birth/death dates) surfaced two more gaps: dates were being chopped mid-value across multiple differently-colored highlight fragments, and Phase 8's deferred finding — a fallback-tier claim's verdict landing on unrelated text and reading as if it were about that text — actually happened (an unrelated claim's fallback guess overlapped a death-date sentence, and its "no evidence found" label was mistaken for a verdict on the date itself).

- [x] T037 `splitClauses` date-comma fix — `matchClaimSpans.ts`: the clause-boundary regex treated the comma in "August 16, 1920" (day/year separator) the same as a real list-separator comma, chopping dates into separate clauses/highlight fragments. Fixed with a combined lookbehind+lookahead (`(?<!\b\d{1,2}),\s+(?=\d{4}\b)|,\s+(?!\d{4}\b)`) so only a comma actually sandwiched between a 1-2 digit day and a 4-digit year is spared — a lookahead-only first version (`/code-review medium`` finding) wrongly suppressed splitting for any comma before a bare 4-digit number, merging ordinary non-date list clauses too (e.g. "cars, 1500 books, and a boat"). Verified: "August 16, 1920 – March 9, 1984" stays intact as one span; "1500 books" in a non-date list still gets its own clause.
- [x] T038 Fallback-tier visual distinction — resolves Phase 8's deferred finding. `matchClaimSpans.ts`: `MatchTier` and the tier of the winning match are now exported on each returned `Span` (`tier?: MatchTier`). `HighlightedArticle.tsx`: a `Fallback`-tier span gets a dashed underline (code-review finding: reuses the existing `FAILED_STYLE`/`UnconfirmedDot`/`FailedDot` dashed "not confirmed" idiom instead of a one-off dotted convention) plus a tooltip note (forced open even with zero sources, so it's reachable), on top of its normal verdict color/icon — so the coverage guarantee ("every claim highlighted somewhere," T031) no longer implies precision a fallback guess doesn't have. **Revised same day**: the first version of the note just said "not a confirmed match" with nothing else — user feedback: unhelpful, since the highlighted words themselves aren't a reliable stand-in for the claim (that's the definition of fallback), it gave the user no way to tell what was actually checked. Now shows the claim's own extracted text ("the claim actually checked here was: '...'") instead, in both the tooltip and the sr-only text. New tests in `matchClaimSpans.test.ts` assert `tier` is `Exact`/`Fallback` as expected.
- [x] T040 Grounnel document title — `App.tsx`: `/grounnel` inherited `index.html`'s static Biassemble tab title (no code anywhere set it per-route). Since there's no client-side router and every cross-nav link (`BiassembleLayout.tsx`) is a plain `<a>` that full-reloads, a one-time `document.title` set in a `useEffect` keyed on `isGrounnelRoute()` is sufficient — no per-navigation update needed.
- [x] T039 `sourceLabel.ts` domain-only fix — always renders the source's domain, never the page title, in both the tooltip and the References list; previously `title || domain` produced an inconsistent mix (some entries a clean domain, others a full article headline) within one Wikipedia-style list. `/code-review medium` finding: this only covered `CitationQuote.tsx` (via `sourceLabel()`) — `SourceLink.tsx`, rendered in the same `HighlightedArticle.tsx` tooltip for sources not covered by a citation, still did `title || domain`; fixed to match (attached-document sources, which have no domain, are unaffected).

**Checkpoint**: `tsc -b` clean, `matchClaimSpans.test.ts` 18/18 passing. `/code-review medium` run against this phase's diff — 3 findings, all applied: the two above plus the `sourceLabel` gap in `SourceLink.tsx`.

## Phase 11: Bare-domain titles, reference-count inflation, unconfirmed-source clarity, heading highlights

**Goal**: four more real-run findings, none touching prior task scope.

## Phase 12: `/code-review high` fixes for T047's heading exclusion

**Goal**: `/code-review high` against T047's diff found a **confirmed, reproduced crash** plus several real precision/consistency issues in the same change; all but two lower-priority/deferred ones fixed here.

- [x] T048 Fixed the confirmed crash — when `isHeadingLike()` excluded EVERY sentence in an article (a short heading-only stub, or any article where nothing survives the filter), `sentenceCandidates`/`clauseCandidates` were both empty and the fallback tier's `ranked[0]!` was an unchecked `undefined`, throwing `Cannot read properties of undefined (reading 'start')` out of the overlap-sort comparator the moment a second claim needed the same fallback path — reproduced live before fixing. `findSentenceMatch()` now also builds unfiltered `allSentenceCandidates`/`allClauseCandidates` twins and degrades to them only when the filtered (non-heading) lists are empty, so "every claim gets a real span" holds even for a heading-only article. New regression test.
- [x] T049 `assignHomeSentence()` now applies the same heading-avoidance as `matchClaimSpans()` (degrading to headings only when literally nothing else is available) — previously it shared `splitSentences()`'s output with no filter at all, so a claim's progress-dot grouping could point at a heading that the article body would never actually highlight it against. New regression test.
- [x] T050 `isHeadingLike()` now counts CONTENT words via this file's own `tokenize()` instead of a raw whitespace split, which disagreed with it — a stopword-heavy title ("The Rise And Fall Of The Empire", 7 raw words) was NOT recognized as heading-like even though its real content-word count (3) clearly is. New regression test.
- [x] T051 `splitSentences()`'s newline boundary is now `\r?\n+`, not just `\n+` — a CRLF-ended line was leaving a stray trailing `\r` attached to the preceding sentence's text (harmless today since `trim()` runs before classification/comparison, but a latent landmine).
- [x] T052 Named the `6`-word heading threshold as `HEADING_MAX_CONTENT_WORDS` with the same "not tuned by measurement, revisit if wrong" disclaimer this file already uses for `JACCARD_THRESHOLD` — was an untuned magic number with no such flag.
- Deferred, not fixed: (1) `isHeadingLike` still won't catch a heading containing internal punctuation (an abbreviation or quoted exclamation) — hard to distinguish cheaply from real mid-sentence punctuation without over-fitting; (2) `splitClauses()`'s "and"/"but" boundary can still carve a degenerate 1-word fragment out of ordinary body prose containing those words (e.g. "Salt and pepper..."), not just headings — the deeper, more general fix (a minimum-content-word guard on any Sentence/Clause/Fallback candidate) risks breaking existing legitimate short matches (e.g. the "six novels" clause test) without careful separate tuning; (3) `isHeadingLike`/`tokenize` still gets recomputed once per claim instead of once per article — real but negligible at realistic claim counts (~30 claims × ~150 sentences is sub-millisecond), pre-existing pattern this diff added one more instance of rather than introduced.

## Phase 13 — D028: consume `biassemble-core`'s verified `source_excerpt`, delete the guessing machinery

**Goal**: `biassemble-core` (branch `011-gr-upd1`, D028) now returns a verified, verbatim `source_excerpt` per claim instead of leaving the frontend to reverse-engineer a claim's location from its paraphrased text. User direction: "LET core cut text. FE should not do that." — stop patching `matchClaimSpans.ts`'s guessing heuristics one bug at a time; consume the new field as the primary locator and delete the machinery (clause-splitting, heading detection, degenerate-fragment filtering) that existed only to patch that guessing approach's own failure modes.

- [x] T054 `Claim.sourceExcerpt` type — `frontend/src/types/grounnel.ts`, mirroring `biassemble-core`'s new additive/defaulted field (via `backend/src/lib/ai/contracts.ts`'s `grounnelClaimSchema`, updated the same way as `citations` was for D027).
- [x] T055 `matchClaimSpans.ts` rewrite — DELETED `splitClauses`, `isHeadingLike`, `HEADING_MAX_CONTENT_WORDS`, `clauseHasEnoughContent`, and the `Clause`/`Fallback`-as-distinct-tier split (down to 2 tiers: `Exact`, `Sentence`) — all existed specifically to patch failure modes of guessing a claim's location from paraphrased text alone, which is no longer how the primary path works. NEW primary path: `findSourceExcerptSpan` — a plain `articleText.indexOf(sourceExcerpt)` (safe now that core guarantees a strict, exact substring), falling back to a new `findNormalizedSpan` only when that misses (a rare secondary path for e.g. a line-ending/whitespace difference introduced in transit) — built via a real index map into the ORIGINAL string (`buildNormalizedIndexMap`), so a normalized-path match's `start`/`end` are always genuine offsets into `articleText`, never offsets shifted by an intermediate normalized copy (the coordinate-mapping bug an external review of the design caught before this was implemented). Fallback path (`findFallbackSentenceSpan`, only reached when `source_excerpt` is null/unlocatable): whole-sentence Jaccard, no threshold — kept deliberately minimal per the user's explicit "keep some fallback" answer to the reversal question, and structurally incapable of the old degenerate-fragment/heading bug class since a `splitSentences()` sentence is never a single stray word by construction. `assignHomeSentence` lost its `isHeadingLike` dependency (forced by the deletion, not a separate behavior change) and reverted to plain closest-sentence-by-score grouping. `HighlightedArticle.tsx`'s `isFallback` dashed-underline treatment kept, now keyed off `tier === MatchTier.Sentence` (renamed from `MatchTier.Fallback`).
- [x] T056 `matchClaimSpans.test.ts` rewrite — removed clause-splitting/heading/degenerate-fragment cases (dead code paths); kept overlap-resolution and fallback-tier cases, retargeted at the new tier semantics; added: `source_excerpt` exact-match (Exact tier), excerpt-not-found-degrades-to-fallback, a documented behavior-change case (a compound sentence with no `source_excerpt` now falls back to the WHOLE sentence, not a clause), the normalized secondary path returning real original-text coordinates (not a normalized/reconstructed string), and a duplicate-occurrence case (a `source_excerpt` appearing twice resolves to the first occurrence, documented `indexOf` semantics). 15/15 passing.
